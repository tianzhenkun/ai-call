# 回复停滞与取消无确认的恢复

两通生产通话暴露了相同的本地缺口：`call_367171092849741824` 在回复开始、只生成“好的”后停滞，客户约 6.5 秒后才打断；`call_367191336657997824` 则在回复开始事件到达前取消。两者均未收到回复结束事件，`active/cancel_pending` 一直占用回复调度，后续识别成功的发言只能排队。已有日志不能确定最初缺少结束事件的上游原因。

## 恢复行为

- 正常回复立即发送，不增加固定等待。输出或播放有进展时更新计时；连续 8 秒没有进展才处理为停滞。
- 先停旧音频并请求取消。收到结束确认后，在原连接回答待处理问题；取消 2 秒未确认则关闭旧连接，重新配置独立连接并恢复近期对话。
- 重建阶段限时 5 秒，音频上传等待切换完成。先完成正在执行的发言审核，再取已接受的客户文字。客户仍在讲话时等其停说，用最新问题触发回复。
- 旧连接、旧回复 ID、旧代次和重复结束事件不能影响新回复。恢复首段音频不再受旧打断保护窗压制。历史 AI 文字标为生成草稿，不假定客户已经听完。
- 每通最多恢复一次。第二次异常、重连失败或旧音频无法清理时结束故障通话；结束前尝试播放固定故障提示，提示与清理合计限时 8 秒。主动挂断会取消恢复和提示。
- 工具执行中不自动重放操作；工具长时间未完成（30 秒）或取消未结束时进入故障结束，避免重复产生外部业务动作。

这些时限是初始恢复上界，不代表基于真实电话延迟分布得出的最佳阈值。真实电话仍需检查误超时、连续补话和恢复后的上下文。

## 诊断

持久化 `model_response_trace` 和 `response_failure_prompt`。记录创建/取消发送时间、供应商会话及回复 ID、原始事件接收、处理、音频分片数量和发布进度；不新增密钥、原始音频或全文请求日志。故障结束使用 `model_error`，失败阶段为 `response_recovery`。

固定提示文件为 `static/ai-call/audio/response-unavailable.wav`，文字为“抱歉，通话服务暂时出现故障，请稍后再试。再见。”。它由 macOS 中文 Eddy 语音生成，24 kHz、单声道 PCM16，约 5.24 秒；与正常对话 Tina 音色不同，播放不依赖实时模型。容器构建必须包含该文件。
