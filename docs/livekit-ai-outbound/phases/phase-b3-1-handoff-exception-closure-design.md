# Phase B3.1：转人工异常闭环正式技术设计与实现基线

最后更新：2026-06-17

## 1. 文档定位

本文档是 Phase B3.1 的正式技术设计与实现基线，用于在 Phase B3 最小转人工收口之后，补齐“转人工失败或超时后怎么办”的异常闭环。

当前代码已按本文档完成实现，并通过本地自动化测试；真实通话下的提示音听感、超时自动结束和前端展示仍需手工验收。

B3.1 只解决三个问题：

1. 转人工等待期间如何提示用户。
2. 转人工失败或超时后如何给用户明确提示。
3. 提示后如何自动结束通话，并让通话记录、转人工记录和事件都能解释本次结束原因。

B3.1 不做人工 ASR、坐席排队、坐席在线状态、技能组、坐席工作台、真实 SIP 联调，也不恢复 AI 继续对话。

## 2. 第一性原理

转人工异常闭环的本质不是多播放几句音频，而是避免用户进入不可解释的等待状态。

用户需要知道三件事：

1. 系统已经开始为他接入人工。
2. 如果人工没有接上，系统会给明确结果。
3. 通话不会无限等待。

系统需要满足四个约束：

1. Web 和未来 SIP 都要通用，不能依赖浏览器本地播放提示音。
2. 不能重新拉起大模型或实时 TTS 来播报固定话术。
3. 不能让等待提示音干扰坐席加入后的真人对话。
4. 数据库操作仍然是低频状态变更，不能进入实时音频热路径。

所以 B3.1 的核心不是“循环安抚”，而是：

```text
一次等待提示
  -> 有限等待
  -> 坐席接入则结束异常流程
  -> 坐席未接入或接入失败则播放失败提示
  -> 短延迟后自动结束通话
```

## 3. 设计结论

B3.1 推荐采用“有限等待 + 等待回铃声 + 自动结束”的最小方案：

1. 转人工触发后直接停止 AI 对话态，进入系统转接等待态。
2. 播放固定等待声 `handoff-ringback.wav`，直到坐席接通、取消、失败或超时。
3. 将转人工等待超时时间配置化，B3.1 验证建议默认 30 秒，生产可按坐席 SLA 调整。
4. 转人工失败或超时后，停止等待声并直接自动结束通话。
5. 不再播放第二段固定人声提示，也不额外延迟 2 秒。
6. `ai_call_handoff` 不新增字段、不新建表，复用现有 `status/end_reason/failure_stage/failure_message`。
7. `ai_call_record.end_reason` 使用稳定原因，例如 `handoff_failed`、`handoff_timeout`。
8. 系统音频播放能力仅用于等待回铃声。

## 4. 等待过程提示策略

### 4.1 推荐策略

等待人工接听时，推荐默认策略是：

1. 发起转人工后，直接进入等待态，并播放固定等待声。
2. 不再请求模型生成转人工提示。
3. Web 验证页显示等待状态和剩余时间。
4. 如果坐席在超时前接入，停止等待声和异常等待流程。
5. 如果超时仍未接入，先停止等待声，再直接自动结束。

### 4.2 为什么不默认循环播报

不建议 B3.1 默认每隔几秒循环播报“请继续等待”。

原因：

1. 转人工不是传统客服排队系统，当前没有真实队列长度、坐席在线状态和预计等待时间。
2. 循环播报容易在坐席刚接入时和真人声音重叠。
3. 等待音乐或循环语音会进入录音，影响后续复盘体验。
4. B3.1 的目标是异常闭环，不是建设 IVR 排队体验。
5. 如果需要长时间排队，应该先建设坐席在线状态和队列能力，而不是用循环音频掩盖。

### 4.3 如果必须支持长等待

如果未来真实坐席队列上线，且业务允许用户等待超过 45 秒，可以单独扩展“等待提醒”能力：

1. 每 20-30 秒最多播放一次短提醒。
2. 最多提醒 1-2 次。
3. 坐席一旦 `accepted` 或 `connected`，立即停止后续等待提醒。
4. 等待提醒必须由服务端系统音频发布，不能由浏览器本地播放。

这个能力不放入 B3.1 默认实现。

## 5. 预制音频设计

### 5.1 当前默认音频

当前默认只使用等待回铃声：

| 文件 | 用途 | 播放时机 |
|---|---|---|
| `handoff-ringback.wav` | 转人工等待回铃声 | 模型播报“正在接入人工”后，等待坐席接入期间播放 |

`handoff-waiting.wav` 和 `handoff-unavailable.wav` 不进入默认运行链路。

### 5.2 不再新增失败人声提示

B3.1 不再要求播放“暂时未能接入人工，本次通话稍后将结束。”这类固定人声提示。

原因：

1. 固定人声音色很难和当前模型音色保持一致。
2. 失败/超时场景应尽快确定地结束，不应增加额外播报等待。
3. 转人工入口已经由模型用当前音色说明“正在接入人工”，等待阶段有回铃声即可表达状态。

### 5.3 音频格式

继续使用与 B3 一致的格式：

1. `wav`
2. mono
3. 16-bit PCM
4. 推荐采样率 24000 Hz

## 6. 系统音频播放能力

### 6.1 当前问题

B3 的转人工提示曾由固定音频播放，当前已改为优先由模型按当前通话音色播报。

等待阶段仍需要服务端发布固定回铃声。

原因：

1. 转人工提示播报后，AI Agent 会被停止。
2. 转人工超时或失败可能发生在 Agent 停止之后。
3. 等待回铃声不能依赖已经停止的 AI Agent。
4. 等待回铃声需要进入同一个 LiveKit Room，后续 Web 和 SIP 场景都能复用。

### 6.2 推荐方案

B3.1 增加一个轻量的系统音频播放器：

```text
AiCallSystemPromptPlayer
```

职责：

1. 按 `room_name` 加入指定 LiveKit Room。
2. 发布一条临时系统音频轨道。
3. 播放本地等待回铃声 wav 文件。
4. 播放完成后断开临时 Participant。
5. 记录等待回铃声开始、停止或失败事件。

推荐系统 Participant 身份：

```text
system-audio-{call_id}
```

注意：

1. 它不是 AI Agent。
2. 它不连接模型。
3. 它不订阅用户音频。
4. 它只发布固定系统等待声。
5. 它可以复用 B3 的 wav 解码和 PCM 分帧逻辑，但不复用 Agent 生命周期。

### 6.3 为什么不用浏览器本地播放

不能使用浏览器本地播放等待回铃声。

原因：

1. 未来 SIP 用户没有浏览器。
2. 录音里可能录不到浏览器本地等待声。
3. 服务端无法保证等待声真正被播放。
4. 接管状态和媒体提示会分裂，排障困难。

### 6.4 为什么不用实时 TTS 或固定结束人声

B3.1 不使用实时 TTS，也不默认播放固定结束人声。

原因：

1. 实时 TTS 会引入额外延迟、成本和失败点。
2. 固定结束人声会带来音色不一致问题。
3. 超时/失败时直接结束比“再解释一次后再挂断”更简单稳定。

## 7. 状态与结束策略

### 7.1 超时策略

B3 已有 `expires_at` 和懒过期。

B3.1 要实现自动结束，仅靠懒过期不够，因为如果用户和前端都不再查询，系统不会主动触发结束。

推荐新增运行态超时任务：

1. 创建 handoff 后，为该 `handoff_id` 启动一个运行态 timeout task。
2. task 睡眠到 `expires_at`。
3. 到期后再次读取 handoff 当前状态。
4. 如果状态仍是 `requested` 或 `accepted`，标记为 `expired`。
5. 停止等待回铃声。
6. 直接结束通话。
7. 如果坐席已 `connected/completed/canceled/failed`，task 直接退出。

这个 timeout task 属于当前实时通话运行态，不是数据库轮询任务。

### 7.2 失败策略

以下场景进入失败闭环：

| 场景 | handoff 状态 | 通话结束原因 |
|---|---|---|
| 坐席 Token 签发失败 | `failed` | `handoff_failed` |
| 坐席加入 Room 失败并调用 fail 接口 | `failed` | `handoff_failed` |
| 等待坐席接管超时 | `expired` | `handoff_timeout` |
| 坐席 accepted 后迟迟未 connected | `expired` | `handoff_timeout` |

### 7.3 自动结束策略

失败或超时后：

1. 先记录 `handoff_failed` 或 `handoff_expired`。
2. 停止等待回铃声。
3. 调用现有结束通话链路。
4. 停止录音。
5. 完成 `ai_call_record`。
6. 记录自动结束事件。

## 8. 配置设计

B3.1 推荐增加以下配置：

| 配置 | 默认值 | 说明 |
|---|---|---|
| `AI_CALL_HANDOFF_TIMEOUT_SECONDS` | `30` | 转人工等待超时时间；可按生产坐席 SLA 调整 |
| `AI_CALL_HANDOFF_EXCEPTION_CLOSE_ENABLED` | `true` | 是否启用失败/超时自动结束 |

说明：

1. `AI_CALL_HANDOFF_TIMEOUT_SECONDS` 应替代当前 `AiCallHandoffService` 构造中的硬编码默认值。
2. 本阶段不新增数据库配置表。
3. 本阶段不做租户级配置。
4. 如果配置关闭自动结束，只记录失败或超时，不主动挂断；但这不是推荐生产行为。

## 9. 数据设计

B3.1 不新增表、不新增字段。

复用：

1. `ai_call_handoff.status`
2. `ai_call_handoff.end_reason`
3. `ai_call_handoff.failure_stage`
4. `ai_call_handoff.failure_message`
5. `ai_call_record.status`
6. `ai_call_record.end_reason`
7. `ai_call_event`

推荐原因值：

| 场景 | handoff status | handoff end_reason | call end_reason |
|---|---|---|---|
| 转人工超时 | `expired` | `timeout` | `handoff_timeout` |
| 转人工失败 | `failed` | `token_issue` / `agent_join` / `agent_suspend` | `handoff_failed` |
不增加 `handoff_exception_policy_id`、`prompt_config_id`、`queue_id`、`retry_count`。

## 10. 事件设计

B3.1 复用 B3 事件，并新增以下低频事件：

| 事件类型 | source | 触发时机 |
|---|---|---|
| `handoff_timeout_task_started` | `handoff` | 创建 handoff 后启动运行态超时任务 |
| `handoff_timeout_task_canceled` | `handoff` | handoff 进入非超时终态或通话结束 |
| `handoff_auto_end_scheduled` | `handoff` | 已计划自动结束通话 |
| `handoff_auto_ended` | `handoff` | 已因 handoff 异常自动结束通话 |

事件 payload 示例：

```json
{
  "handoffId": "handoff_325...",
  "status": "expired",
  "reason": "handoff_timeout"
}
```

事件只保存排障必要信息，不保存完整用户原文、录音内容或敏感业务信息。

## 11. 接口影响

B3.1 不新增公开接口。

复用现有接口：

1. `POST /ai-call/sessions/{callId}/handoffs`
2. `GET /ai-call/sessions/{callId}/handoff`
3. `POST /ai-call/handoffs/{handoffId}/accept`
4. `POST /ai-call/handoffs/{handoffId}/connected`
5. `POST /ai-call/handoffs/{handoffId}/complete`
6. `POST /ai-call/handoffs/{handoffId}/cancel`
7. `POST /ai-call/handoffs/{handoffId}/fail`

行为变化：

1. 创建 handoff 后启动超时任务。
2. fail 接口标记失败后触发异常闭环。
3. 查询当前 handoff 时如果懒过期，也应触发异常闭环。
4. connected、complete、cancel、通话结束时取消超时任务。

HTTP 接口不应等待自动结束任务全过程完成。

推荐做法：

1. 接口先返回状态变更结果。
2. 后台 task 执行等待声停止和自动结束。
3. 前端通过刷新状态、事件列表和通话状态看到最终结果。

## 12. 前端验证页改动

继续基于 Phase A 静态页扩展，不新增页面。

推荐改动：

1. 转人工状态区域展示 `expiresAt` 和剩余等待秒数。
2. 状态为 `requested` 或 `accepted` 时显示“等待人工接入”。
3. 状态为 `expired` 或 `failed` 时显示“人工暂未接入，通话已结束”。
4. 自动结束后显示通话结束原因。
5. 不新增“播放失败提示音”按钮。
6. 不新增循环等待音频开关。

Web 页面可以显示倒计时；SIP 用户没有页面，等待状态以服务端回铃声为准。

## 13. 与录音和对话文本的关系

### 13.1 录音

1. 等待回铃声应进入同一个 LiveKit Room。
2. 因此录音里能听到等待声。
3. 自动结束后仍走现有录音停止和文件索引流程。

### 13.2 对话文本

B3.1 不要求把系统提示音写入 `ai_call_dialogue_segment`。

原因：

1. 它不是 AI 对话，也不是用户或人工说话。
2. 系统提示已经有事件可复盘。
3. 若后续需要完整通话字幕，再单独设计 `speaker_type=system` 是否进入文本段。

## 14. 与 SIP 的关系

B3.1 对未来 SIP 通用。

原因：

1. 提示音由服务端加入 LiveKit Room 播放。
2. SIP 用户最终也是 Room 里的 Participant。
3. 自动结束调用的是通用结束通话链路。
4. 录音、事件、handoff 状态仍按 `call_id` 关联。

不能使用浏览器本地提示或前端计时作为核心能力，否则 SIP 场景会失效。

## 15. 并发与资源

B3.1 不进入实时模型热路径。

资源影响：

1. 每个等待中的 handoff 最多一个运行态 timeout task。
2. 失败或超时时短暂创建一个系统音频 Participant。
3. 系统音频播放完成后立即释放。
4. 没有数据库轮询。
5. 没有实时 TTS 或模型调用。

如果服务进程重启：

1. 运行态 timeout task 会丢失。
2. 现阶段可由查询时懒过期兜底。
3. 多实例和重启恢复属于 Phase D 生产加固，不放入 B3.1。

这个取舍与当前实时会话本身的进程内运行态一致，不额外扩大风险。

## 16. 实施顺序

建议按以下顺序实现：

1. 增加 B3.1 配置项。
2. 增加系统等待回铃声播放器。
3. Handoff 创建后注册超时任务。
4. connected、complete、cancel、end session 时取消超时任务。
5. fail 或 expired 时触发异常闭环任务。
6. 异常闭环任务停止等待回铃声。
7. 立即调用现有结束会话链路。
8. 前端展示 `expiresAt` 和等待倒计时。
9. 增加事件白名单和自动化测试。

## 17. 自动化测试建议

至少覆盖：

1. 创建 handoff 后启动超时任务。
2. connected 前超时会标记 `expired`。
3. accepted 后超时也会标记 `expired`。
4. connected 后不再触发超时自动结束。
5. cancel 后不再触发超时自动结束。
6. fail 后直接触发自动结束。
7. 自动结束后 `ai_call_record.end_reason=handoff_timeout` 或 `handoff_failed`。
8. 不产生失败提示音事件。
9. B1/B2/B2.5 现有测试不回退。

## 18. 手工验收清单

### 18.1 超时自动结束

1. 创建通话。
2. 点击发起转人工。
3. 听到等待回铃声。
4. 不点击“一键坐席接入”。
5. 等待超时。
6. 通话自动结束。
7. 查询 handoff 状态为 `expired`。
8. 查询通话结束原因为 `handoff_timeout`。
9. 录音可播放，并包含等待回铃声，不包含失败提示人声。

### 18.2 失败自动结束

1. 创建通话。
2. 发起转人工。
3. 模拟坐席加入失败或调用 fail 接口。
4. 通话自动结束。
5. 查询 handoff 状态为 `failed`。
6. 查询通话结束原因为 `handoff_failed`。

### 18.3 成功接管不误伤

1. 创建通话。
2. 发起转人工。
3. 在超时前点击“一键坐席接入”。
4. handoff 状态进入 `completed`。
5. 超时任务不应再结束通话。
6. 录音继续完成。

## 19. 不做事项

B3.1 明确不做：

1. 循环等待音乐。
2. 默认周期性等待播报。
3. AI 恢复对话。
4. 人工坐席 ASR。
5. 坐席排队和在线状态。
6. 多坐席调度。
7. SIP 真实线路联调。
8. 新增 handoff 配置表。
9. 租户级转人工策略。

## 20. 结论

B3.1 推荐做的是异常闭环，不是完整客服排队体验。

最终用户体验应是：

```text
进入等待回铃声
  -> 等待有限时间
  -> 如果人工接入，进入人工通话
  -> 如果人工未接入，直接自动结束通话
```

这样既解决了“失败后不清楚发生了什么”的问题，也避免为了等待过程引入循环播报、等待音乐、坐席队列和登录态等过度设计。
