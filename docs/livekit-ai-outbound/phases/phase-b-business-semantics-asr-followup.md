# Phase B 后续：业务语义与 ASR 识别准确率问题记录

最后更新：2026-06-24

## 1. 当前结论

当前不切换实时模型，不新增模型路由，也不修改主通话链路。

本记录只作为后续业务语义与 ASR 准确率评估输入。后续可考虑引入豆包等其他实时语音模型做同样样本的对比测试，但不能在没有样本指标前直接替换当前 `qwen3.5-omni-plus-realtime`。

## 2. 已确认的模型边界

当前实时通话主链路使用阿里百炼 `qwen3.5-omni-plus-realtime`。

当前实时用户转写来自 Qwen-Omni-Realtime 会话内置的 `input_audio_transcription`。按阿里云官方文档，Qwen-Omni-Realtime 的语音转录模型为固定的 `qwen3-asr-flash-realtime`，不支持通过 `session.update` 修改。

当前未发现 Qwen-Omni-Realtime 的 `session.update` 支持 `hotwords`、`phrase_hints`、`vocabulary_id`、`glossary` 等热词或术语提示参数。

阿里云语音识别热词能力主要适用于 Fun-ASR、Paraformer 系列；项目中的 `paraformer-v2` 属于通话后离线 ASR/复盘链路，不参与当前实时 AI 回答。

## 3. 最新样本观察

样本：`call_328159153691185152`

验证目标：业务词和时间表达。

观察结果：

1. `GEO` 被实时转写为 `CEO`。
2. `GEO` 被实时转写为 `Z O`。
3. `生成式引擎优化` 被实时转写成类似“远程优化”“智慧城市远程优化”的表达。
4. `下周二`、`下周二下午`、`多长时间` 这类时间和时长表达基本可识别。
5. AI 能在部分上下文里把 `Z O 是什么` 拉回到 GEO 解释，但对“智慧城市远程优化是什么”没有稳定澄清。
6. 客户只说“好的”时，AI 擅自把预约时间定成“下周二下午两点”，时间确认逻辑仍需单独治理。
7. 客户后续说“挂了吧/不用了”时，系统检测到结束意图，但最终 `end_reason` 为 `normal_completed`，说明已完成任务后的结束原因优先级后续也可单独评估。

## 4. 风险判断

这不是单纯提示词问题，也不是转人工状态机问题。

根因更接近实时 ASR/端到端模型对业务术语的识别不稳定。当前业务词错误会进入后续对话上下文，导致 AI 回答偏离真实用户问题。

如果只做简单字符串替换，例如把所有 `CEO` 都改成 `GEO`，会误伤真实 CEO 场景，不适合作为通用修复。

## 5. 后续候选方向

后续可按以下顺序评估：

1. 保持当前 Qwen-Omni-Realtime 主链路，先做本地业务词候选纠错和低置信澄清。
2. 引入独立实时 ASR 旁路，例如 Fun-ASR 或 Paraformer Realtime，并使用热词能力辅助识别业务术语。
3. 使用同一批录音样本对比其他实时语音模型，例如豆包实时语音模型，重点比较业务词、时间表达、转人工/挂断意图、延迟、打断体验、工具调用稳定性和成本。
4. 若后续切到“三段式 ASR -> LLM -> TTS”或“旁路 ASR 驱动语义”的架构，必须重新评估首包延迟、打断、上下文同步和通话自然度。

## 6. 暂不处理范围

当前暂不处理：

1. 不切换模型。
2. 不新增多模型路由。
3. 不把豆包或其他模型接入主链路。
4. 不修改 `intro_geo` 提示词。
5. 不做无条件 ASR 文本替换。

## 7. 后续评估指标

后续如果启动模型或 ASR 对比，应至少记录：

1. 业务词准确率：`GEO`、`生成式引擎优化`、`SEO`、产品名、人名、公司名。
2. 关键语义准确率：转人工、挂断、预约时间、拒绝、稍后联系。
3. 实时延迟：首包、用户停顿到 AI 回复、转写 final 延迟。
4. 打断体验：用户插话后 AI 停止速度、迟到音频、重复回复。
5. 工具调用准确率：`request_handoff`、`schedule_call_end` 是否漏触发或误触发。
6. 成本和稳定性：单通成本、并发限制、Web/LAN 与 SIP 差异。
